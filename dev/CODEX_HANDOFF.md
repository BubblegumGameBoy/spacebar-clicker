## 1. リポジトリと環境の準備

```
git clone https://github.com/BubblegumGameBoy/spacebar-clicker && cd spacebar-clicker
# 開発ソース 2/・新しいテスト・QAツールはgit管理外。アーカイブから展開する。
tar -xzf dev/sequel-source.tar.gz        # 公開済みの版（M1〜M3, M6まで）
tar -xzf dev/sequel-source-wip.tar.gz    # 作業途中の版（M4・M5の途中を含む）。こちらを上に重ねて展開する
node --test test/*.test.cjs              # Node 22 では --test-isolation=none は付けない
```

- **ブラウザ**：QAスクリプトの多くが `/usr/bin/chromium` を決め打ちしている。Playwright の chrome へ symlink を張る（例：`ln -sf /opt/pw-browsers/chromium-*/chrome-linux64/chrome /usr/bin/chromium`）。
- **ビルド**：`python3 tools/build_playtest.py <出力先>` → `python3 -m http.server <port> --directory <出力先>` → `http://127.0.0.1:<port>/preview/`
  - `?lesson=1` を付けると、新規体験用の別セーブ。
  - QAスクリプトは環境変数 `GAME_URL` で接続先を変えられる。
- **git管理外のもの**：`2/`、`test/` と `tools/` の新規ファイルは `.git/info/exclude` に入れる（`/2/`, `/test/`, `/tools/`）。理由は、repo の root がそのまま GitHub Pages で公開されるため。`2/` を commit すると `/spacebar-clicker/2/` が公開されてしまう。

## 2. 公開の手順（必ずこの順）

1. `2/index.html` の `?v=` をすべて新しい版名に置き換える（例：`20261026-m3m6` → `20261027-m4m5`）。上げないと、以前遊んだ人のブラウザで新旧のファイルが混ざる。
2. ビルドし、`preview/` に `media/` 以外を上書きコピーする。
   - 新しい画像は `assets/` に置く。ビルドは追跡済みの画像を、公開先に無い時だけコピーするので、`assets/` の実ファイルを更新して commit する。
3. 起動の確認：PC・`?lesson=1`・スマホ幅のタッチの3構成で、pageerror と HTTP エラーが0件であること。
   - BGM の mp3 で `ERR_ABORTED` の後に 206 が返るのは、ブラウザの正常な挙動。
4. 主要QAを通す：qa_ground_journey, qa_harvest_skills, qa_m3_legacy_save, qa_enemy_roster, qa_manual_rails, qa_unified_placement（と、新しいマイルストーンのQA）。
5. `dev/sequel-source.tar.gz` を詰め直す。中身は `2/` 全部と、git管理外の `test/`・`tools/` のファイル（旧アーカイブの一覧も含める）。scratch のセーブやプレイヤーIDは入れない。
6. `dev/SEQUEL_HANDOFF.md` の冒頭の「方針転換」節に要点を足す。
7. commit して `git push origin main`。GitHub Pages の配信成功を `gh run list` で確認する。
   - 公開URL：https://play.bubblegumgameboy.com/spacebar-clicker/preview/
   - 元のゲーム（root の `index.html`、Worker、package）は変更しない。

## 3. 守ること

**ユーザーの判断軸**：連打の手応え／仲間が実際に増える見た目／自分で作る自動化／前の苦労が楽になる成長／編成と配置の選択。

**禁止**：
- 味方の勝手な歩き回り
- 常時の画面揺れ・全画面の演出
- 主人公のHP
- コンベア経路の自動建設
- 個別資材を「×32」などの束にまとめること
- 数の表記に「×」を使うこと（「1人」「N体」と書く）

**その他**：
- 日・英・中の3言語を必ず揃える。
- 実プレイ（新規セーブから見える操作だけ）と、準備済みの機能試験（資材付与・状態編集）を区別して記録する。
- CDP のタッチは「実機ではない」と書く。音を耳で聞いていなければ、試聴済みとは書かない。
- 参考作（grmchn/dopa-drill）のコード・素材・曲は移植しない。原理だけを使う。

### M5 の調整で次にやること（オーナー不在の間にメイン担当が決めた基準）

- **脅威度1（各条件を単独で）のWave9**：
  - 記録上の完走編成では負けてよい。
  - 対策を意識した手の届く強化（4枠をすべて使う・増員を1段階上げる・方針や配置の変更）をすれば、援護なしでも勝てるようにする。
  - 援護あり（Space を毎秒4回程度）なら、強化の前でも勝つか、惜しい（箱1、または撃破8割以上）。
- **脅威度2〜3**：対策の組み合わせと援護の両方があれば勝てる構成が、1つはある。
- **脅威度4以上**：模型（固定dt）で、勝てる構成が1つはあることを示す。
- **Wave4**：脅威度1の各条件で、対策すれば援護なしでも勝てる。
- **そのほかの課題**：
  - 「地中から」：Wave4で、角に寄せる対策をしても勝てない。
  - 「狭い陣地」：完走編成が3枠だと判断が変わらない。封鎖する枠を、使っている枠から選ぶ案がある。
  - 実時間のブラウザと固定dtの模型の差の原因を調べる。
  - 「急襲」の戦闘結果を試す。

### 既知の課題（どれも未対応）

- 標準的な編成（弓3×2・剣士・バリスタ）では、Wave7（plan v3）に負ける。旧計画でも同じ。
- 送風機1台で約6割が届く。当初の目標3〜5割より甘い。通しプレイで調整する。
- 送風機の羽根は回転しない。羽根だけを分けた絵を codex に頼めば解決する。

## 6. 進め方（このプロジェクトで効いたやり方）

1. **役割を分ける**：
   - director：優先順位・完成条件・数値の基準を決める。
   - copy cat：他ゲームの定番の構造を棚卸しする。オーナーから「パクリが甘い」と叱られたので、珍しい作品の細かい話より、ジャンルの定番を先に網羅すること。
   - ドパガキ：操作に対する音・演出・成功報酬の階層をレビューする。
   - 実装者と、コードレビュー役は別の担当にする。
2. **並行で進める時**は、担当するファイルを明示して分ける（例：搬送系 outpost-camp / supply-factory / ground-physics と、戦闘系 outpost-core / outpost / expedition / army）。`game-core.js` の保存の移行だけは両方が触りうるので、最小限にして行単位で報告させる。
3. **1つのマイルストーンの流れ**：実装 → コードレビュー（再現スクリプト付きで重大な順） → ドパガキの手応えレビュー → 修正 → 公開。レビューでは毎回、資材の消失・二重消費・保存の互換・タッチの互換クリックの不具合が見つかっている。
4. **画像**：オーナーが codex に依頼する。依頼文は `dev/ART_PROMPTS.md` の形式で書く（共通スタイル＋1枚ずつ、透明PNG、1536×1024 か 1024×1024、格子の並びを明記）。受け取ったら、セルごとに不透明部分で切り出し、半分の解像度・非可逆WebP（quality 90、alpha_quality 100）で `assets/` に置く。

## 6.5 最優先の不具合（未修正）

- **襲撃中に Space の援護が効かない場面がある。** 木を選択したままだと、襲撃中でも Space が採集になり、一度敵をクリックするまで攻撃にならない。
  - 援護はこのゲームの主操作で、脅威度の難度は援護を前提に調整してある。最初に直すこと。
  - 関係するのは `2/supply-factory.js`（採集の入力）と `2/outpost.js` の `manual()`。
  - 方針の案：襲撃中は Space を援護（攻撃）に優先して割り当てる。ただし準備中の採集は従来どおりにする。
